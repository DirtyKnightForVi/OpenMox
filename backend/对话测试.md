# 分析：对话失控的原因
                                                 
通读整个对话记录，识别出 4 个独立问题，它们叠加放大了混乱效果。 

## 问题 1：HINT_BLOCK 作为可见消息渲染（信息噪音）
这是最直接的前端问题。 useChat.ts  中 HINT_BLOCK 的处理：                                                                                                                                                      
```typescript
// useChat.ts:113-120 
if (type === "HINT_BLOCK") {
    addMessage({ 
      sender: agentId || "system", 
      text: `[上下文] ${data._hint || ""}`, 
      ... 
    }); 
}
```

设计纲要明确要求  HINT_BLOCK  应折叠为「正在协调…」提示，而非完整消息。当前代码把每个上下文播种事件都渲染成可见气泡，导致聊天区被  [上下文]  刷屏。

对话中出现 数百条  [上下文]  消息 → 用户实际想看的是 momo 和 pm-1 的对话，但被大量噪音淹没。

## 问题 2：多条 @mention 触发多个 Agent → 级联响应 

用户发送：`@momo 和 @pm-1 聊一聊... `
`MentionRouter` 同时路由给 momo、pm-1 两个 Agent。两个 Agent 独立响应：
· momo 以协调者身份启动对话
· pm-1 以产品经理身份参与
· 对话进行中，arch-1 也被唤醒了（可能是被对话中的某些内容触发）
· arch-1 开始执行工具调用（ read  文件等）
· 工具调用结果又产生事件 → 进一步触发更多响应

没有"谁在对话中"的守卫机制 — 一旦多个 Agent 被激活，它们会基于整个对话历史持续响应，形成反馈循环。

## 问题 3：对话历史无限膨胀 → 上下文污染 

momo 和 pm-1 的长对话（广告投放策略）产生大量文本。这本身没问题。但：

1. 每次新响应都把全部历史作为上下文发给 LLM
2. LLM 看到历史后认为"用户还在期待更多" → 继续生成
3. arch-1 看到对话中有"工具调用"的需求 → 加入执行
4. Agent 之间互相看到对方的输出 → 继续接力

结果：对话失控，越来越长，没有自然终止点。

## 问题 4：前端缺失反 spam 机制 

 缺失机制                         表现
 ──────────────────────────────── ─────────────────────────────────────────
 同一 Agent 连续消息合并          同一个 Agent 的多次 [上下文] 消息各自独立
 流式消息节流                     快速涌入的事件逐个渲染，无合并
 长消息截断                       多轮对话后消息数量巨大，无虚拟化
 agent:busy / agent:idle 视觉过滤 状态变化未与消息渲染联动

## 根因优先级排序 

 严重性:   🔴 高  🟡 中  🟢 低 
  
 🔴 HINT_BLOCK 作为可见消息 → 最直接的噪音源 
 🔴 多条 @mention 无并发控制 → 多 Agent 同时响应 
 🟡 没有对话终止条件 → Agent 无限接力 
 🟡 上下文无限膨胀 → token 消耗 + 混乱 
 🟢 前端消息列表无虚拟化 → 大量消息卡 UI 

当前最立竿见影的修复：把 HINT_BLOCK 从可见消息改为折叠提示，这是纯前端改动，且能立刻消除 90% 的视觉噪音。后面的问题涉及后端编排逻辑，需要更谨慎的方案。
